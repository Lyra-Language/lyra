### Wider integers — `i128`/`u128` (and what's explicitly *not* coming)

**[DECIDED 07/25; MVP LANDED 07/27] Add `i128`/`u128`; do *not* add arbitrary-precision bignums or Zig-style arbitrary fixed widths.** These read as one question but are three, with nothing in common in cost or fit. The `i128`/`u128` MVP slice (change-set steps 1 + 2b + 4 + 5) is now in — see the 07/27 Completed entry; the only remaining gap is >64-bit *literals* (steps 2a + 3):

- **`i128`/`u128` — yes.** They are the *most on-brand* numeric addition: fixed-width and identical on every target, exactly the determinism thesis that removed `int`/`uint`. LLVM lowers `i128` natively and the checked-overflow model extends for free (`llvm.{s,u}{add,sub,mul}.with.overflow.i128` exist), so trap-on-overflow, `match`, comparisons, and conversions all key off width as they already do. Bounded, mostly-mechanical work.
- **Arbitrary precision (bignums) — no, not as a primitive; revisit as a stdlib `BigInt`.** It breaks two load-bearing decisions at once: fixed-width primitives (a type's size is known) and trap-on-overflow (a bignum *grows* instead of trapping, so it can't be what plain `i64 + i64` does — it must be a distinct opt-in type). No systems language ships this as a builtin (Rust `num-bigint`, C++ Boost, Go `math/big`). Lyra is well-placed to do the same *later*: a bignum is just another **managed, ref-counted value** (the `IsManaged` machinery that already frees strings and `shared` boxes), so the runtime shape is solved — what's missing is generics + a stdlib to host it, plus a small-int (tagged-inline) optimization before it's fast enough to want.
- **Zig-style arbitrary fixed widths (`i7`, `u3`, `i256`) — skip** unless a concrete use case (bit-level wire protocols, packed hardware registers) shows up. Non-power-of-two widths force load/store legalization and mask/`sext`/`zext` sequences everywhere, and our primitives are *named constants* (`primitives.go`), not a numeric width field — `iN` would mean reworking that representation entirely. Cost/benefit is upside-down for the demand.

**`i128`/`u128` change set** (front-end + backend; the literal-storage decision in (2) is the one real design fork — everything else is mechanical). **Steps 1, 2b, 4, 5 are [DONE 07/27]; 2a + 3 (>64-bit literals + 128-bit folding) remain open:**
1. **Primitive type names** — add `Int128`/`UInt128` to `pkg/types/primitives.go`, then extend the width/signedness/numeric tables that enumerate the widths by hand: `types.IsNumeric` (`types/types.go`), and in the backend `LLVMPrimitive` → `i128`, `IsSignedInt`, `IsNumericConversionTarget`, and the `SizeAndAlign` case (`pkg/backend/llvm/layout.go`; `i128` is 16/16 on the mainstream ABI) + the `layout_test.go` map. Cheap and self-contained.
2. **Literal storage is the load-bearing constraint.** `IntegerLiteralExpr.Value` is a Go **`int64`** and `numeric_literals.go` parses via `strconv.ParseInt(..., 64)`, hard-erroring anything past 64 bits ("exceeds the 64-bit range"), with a single `Unsigned` bit-pattern special-case for `(i64max, u64max]`. So a true `i128` literal (`170141183460469231731687303715884105727`) can't be represented today. Two options: **(a) widen** the literal node to a `big.Int` / hi-lo pair (threads through the collector, printer/golden output, and every `Value`/`Unsigned` reader), or **(b) MVP** — accept `i128`/`u128` as types but restrict *literals* to values that fit `i64`/`u64`, widening only at runtime (usable, but a visible gap on constants). Recommend shipping (b) first, (a) when a >64-bit constant is actually needed.
3. **Compile-time folding is `int64`-bound.** `typechecker/overflow.go` folds and overflow-checks constants in `int64` (`extractIntLiteralValue` returns `int64`); correct `i128` folding needs 128-bit constant arithmetic — deferrable behind the (2b) MVP. The value-range pass (`checker/range_analysis.go`, E020/W011) needs *no* change: it already **widens `u64` to ⊤** because 2^63 doesn't fit `int64`, so `i128`/`u128` get the same conservative full-range treatment — sound (can only miss a diagnostic, never invent one), never a miscompile.
4. **Backend arithmetic — mostly free.** `add`/`sub`/`mul`/`icmp` and the `with.overflow` trap intrinsics all lower for `i128`; `coerceIntWidth`/`applyIntMathOp` generalize since they read the operand's bit width. **Division and floored `%%` need compiler-rt** (`__divti3`/`__udivti3`/`__modti3`/`__umodti3`) — confirm `lyrac build`'s `clang out.ll` link pulls compiler-rt (it does by default via `clang`; only an issue if the link line is ever hand-assembled).
5. **`print`/`println` need a hand-written formatter.** `print.go`'s `formatForPrint` int path uses libc `snprintf` `"%lld"`/`"%llu"`, and there is **no printf specifier for 128-bit** — add a base-10 routine (split into 19-digit `u64` chunks via divmod by 10^19, or repeated divmod), emitted lazily like the other runtime shims.

**Sequencing:** (1) + (2b) + (4) + (5) is a complete, testable slice (types, arithmetic with traps, division via compiler-rt, printable) with only the >64-bit-literal gap open; (2a) + (3) close that gap when a large constant is first needed.

Tests: `pkg/types/unify_test.go` (direct `TypesEqual` cases) + `pkg/analyzer/typechecker/tests/named_tuple_test.go` (construction validation, generics, the motivating cross-name-same-shape case). **Found along the way, left alone (pre-existing, out of scope):** an anonymous tuple/array literal's elements still don't propagate width against a `let` annotation's element types (`let a: (i32,i32) = (1,2)` errors) — a distinct gap from named-tuple nominality. *(The tuple half was fixed 07/16 — see that day's tuple-payload entry; arrays are still open.)*

### 07/13/26
- **`for` loops (backend) + three-clause form end to end.** Backend: `lowerForLoop` (cond/body/post/exit CFG), `break`/`continue` via a `loops []loopCtx` stack (labeled ones walk it), one-armed `if` statements, `MathAssignOpExpr` (`i += 1`) as load/op/store, and a block-termination discipline (`lowerBlockStmts` stops at a sealed block; fall-through `br`s guarded by `end.Term == nil`). - **Context-directed literal-width inference.** An untyped integer literal now takes its concrete width from context instead of always defaulting to i64. New typechecker helper `propagateLiteralType(expr, concrete)` pushes a concrete numeric width onto untyped literal *leaves*, recursing through width-preserving arithmetic (`+ - * / % %%`, unary `-`) and stopping at identifiers/calls/conversions. Wired into five context sites: annotated `let`, a `MathBinaryOp` with a concrete result, numeric comparisons/`==`, `var` reassignment, and the lambda/entry return body.
